## 提交信息规范

### 格式要求

提交信息必须采用**标题行 + 空行 + 编号正文**的多行格式，**scope（模块名）必填**，不允许裸 type。

结构如下：

```
<type>(<scope>): <标题摘要>

1. <改动项一>。
2. <改动项二>。
3. <改动项三>。
```

要求：
- **标题行**：`type(scope): 简要概括`，一句话说清本次提交的核心目标，尽量不超过 30 字，不要以句号结尾。
- **空行**：标题与正文之间必须有一个空行。
- **正文**：使用 `数字.` 编号列表（`1.`、`2.`、`3.` ...），逐条列出本次提交的具体改动点；每条以中文句号结尾。
- 正文条数根据实际改动决定，1 条也要写编号；无法拆分时至少写出 1 条核心改动。
- 不写多余前缀（如「本次提交」「改动如下」），直接用动词开头的短语描述。

### 类型（type）

- `feat` — 新功能
- `fix` — 修复 Bug
- `refactor` — 重构（不改变功能、不修复 Bug）
- `docs` — 文档变更
- `style` — 代码风格调整（空格、缩进等，不影响逻辑）
- `perf` — 性能优化
- `test` — 增加或修改测试
- `chore` — 构建/工具/依赖变更
- `ci` — CI 配置变更
- `revert` — 回退提交

### 范围（scope）

scope 用于标识本次提交涉及的模块，从以下值中选择：

| scope | 说明 |
|-------|------|
| `auth` | 认证模块 |
| `user` | 用户管理 |
| `tenant` | 租户管理 |
| `rbac` | 权限/角色 |
| `audit` | 审计日志 |
| `wiki` | Wiki 模块 |
| `file` | 文件模块 |
| `dashboard` | 仪表盘 |
| `plan` | 套餐/订阅 |
| `notification` | 通知/公告 |
| `oauth` | 第三方登录 |
| `db` | 数据库/迁移 |
| `middleware` | 中间件 |
| `config` | 配置 |
| `deploy` | 部署/运维 |
| `ui` | 前端页面/组件 |
| `api` | 接口/路由 |
| `other` | 跨模块或不明确的变更 |

### 标题行与正文写法

- 标题行：`type(scope): 动词开头的简短概括`，冒号后空一格，不用句号结尾。
- 正文：用 `1.` `2.` `3.` 编号，每条一句话说明一项改动，以中文句号结尾；同一提交涉及多个模块时，可在条目里点明涉及的模块。

### 示例

✅ **正确**：

```
feat(auth): 添加 API Token 管理功能，支持创建、查询和撤销操作

1. 新增 API Token 相关路由和处理器，支持用户创建和管理 API Token。
2. 更新文档，详细说明 API Token 的使用和管理流程。
3. 配置文件中添加 API Token 最长有效期设置，默认 2160h（90天）。
4. 实现 API Token 的验证逻辑，支持与 JWT 令牌的双模式认证。
```

```
fix(user): 修复重置密码链接过期判断不准的问题

1. 修正过期时间使用本地时区导致边界值提前失效的逻辑。
2. 补充对应单元测试覆盖跨天场景。
```

```
chore(deploy): 更新 Docker Compose 镜像版本

1. 升级 meteorx 后端镜像到最新补丁版本。
2. 同步更新 web-admin 镜像 tag。
```

❌ **错误**：
- `feat: 新增功能`（缺少 scope 且无正文）
- `fix: bugfix`（缺少 scope、无正文且描述不清晰）
- `feat(MAAS): 新功能`（scope 不是约定值）
- 只有标题行没有正文（不满足编号正文要求）
